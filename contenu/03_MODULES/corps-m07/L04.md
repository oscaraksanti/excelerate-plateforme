## Le problème

Vous cliquez dans l'interface, et Power Query écrit du code à votre place. Tant que vous cliquez, tout va bien.

Puis arrive le moment où l'interface ne propose pas ce dont vous avez besoin : sauter des lignes jusqu'à trouver un mot, appliquer une règle différente selon la forme du fichier, rattraper une erreur au lieu de s'arrêter. Il faut alors écrire du M.

Et le M est un langage qu'on n'a aucune raison d'apprendre par cœur. Vous en écrirez dix lignes par an.

> **C'est exactement le profil de ce qu'on délègue à une IA : rare, précis, et vérifiable immédiatement.**

## Ce qu'on construit

Une méthode en quatre temps pour obtenir du M juste sans apprendre le M — et le réflexe qui empêche de coller du code qui ne peut pas fonctionner.

## À quoi ressemble le M

Trois choses à savoir, et elles suffisent.

**① Une requête est un `let … in`.** Une suite d'étapes nommées, et le nom de celle qu'on rend à la fin.

```
let
    Source   = Folder.Files(Dossier_Source),
    Fichiers = Table.SelectRows(Source, each Text.StartsWith([Name], "Ventes_")),
    Typees   = Table.TransformColumnTypes(Fichiers, {{"Name", type text}})
in
    Typees
```

**Chaque ligne du volet « Étapes appliquées » est une ligne de ce code.** Renommer une étape, c'est renommer une variable. C'est tout le mystère.

**② `each` veut dire « pour chaque ligne ».** Et `_` désigne la ligne courante. `[Nom]` désigne la colonne `Nom` de la ligne courante.

```
each [Montant_Local] / [Taux_USD]
```

**③ Le M est sensible à la casse.** `Table.SelectRows` fonctionne, `table.selectrows` non. C'est la première cause d'erreur quand on recopie du code.

Ce qu'il **ne faut pas** apprendre : les quelque huit cents fonctions de la bibliothèque. Personne ne les connaît, et c'est ce qui rend l'IA utile ici.

## La méthode en quatre temps

### 1 — Faire le geste dans l'interface, d'abord

Toujours. Même si vous savez que ça ne suffira pas.

Cliquez, produisez une étape qui fait *à peu près* ce qu'il faut sur *un* fichier, et regardez le code dans la barre de formule. Vous avez maintenant du M juste, qui utilise les bonnes fonctions, avec les bons noms de colonnes.

**C'est votre point de départ, et il vaut mieux que n'importe quelle description en français.**

### 2 — Demander de généraliser

```
Voici une étape générée par l'interface de Power Query :

[colle le code de la barre de formule]

Elle fonctionne sur un fichier, mais elle est fragile :
[dis précisément ce qui te gêne — les noms de colonnes
en dur, le nombre de lignes à sauter, l'ordre des
colonnes...]

1. Réécris-la pour qu'elle ne dépende plus de
   [ce qui te gêne].
2. Explique-moi chaque fonction que tu utilises et ce
   qu'elle fait, en une ligne chacune.
3. Dis-moi ce qui se passe si [le cas limite : une
   colonne absente, une table vide, une valeur nulle].
4. Donne-moi le code final en un seul bloc, prêt à
   coller dans l'éditeur avancé.
```

Le point 2 est celui qui vous fait progresser : au bout de dix fois, vous connaissez les quinze fonctions qui servent vraiment.

### 3 — Écrire une fonction sur description

```
Écris-moi une fonction M personnalisée.

Elle prend : [les arguments, avec leur type]
Elle rend : [ce qu'elle doit produire, précisément]

Les cas qu'elle doit traiter :
- [cas 1 : le format standard]
- [cas 2 : le fichier avec un titre avant les en-têtes]
- [cas 3 : le tableau croisé]

Contraintes :
- aucune colonne désignée par sa position
- les colonnes manquantes sont créées à vide plutôt
  que de faire échouer la fonction
- les types sont posés explicitement à la fin

Commente chaque étape en français.
```

Les trois contraintes sont à recopier telles quelles à chaque fois. Sans elles, vous obtiendrez du code qui marche sur votre exemple et casse le mois suivant.

### 4 — Déboguer un message d'erreur

Les messages du M sont parmi les plus obscurs d'Excel :

> *« Expression.Error : la colonne 'Montant_Local' du tableau est introuvable. »*
> *« DataFormat.Error : nous n'avons pas pu convertir en nombre. »*
> *« Expression.Error : nous ne pouvons pas appliquer l'accès de champ au type List. »*

```
Power Query me rend cette erreur :
[colle le message, entier, sans le raccourcir]

Voici l'étape sur laquelle elle apparaît :
[colle le code de l'étape]

Voici les étapes précédentes :
[colle les deux ou trois d'avant]

1. Explique-moi ce que dit vraiment ce message.
2. Donne-moi les deux causes les plus probables, dans
   l'ordre.
3. Pour chacune, comment je la vérifie en trois
   secondes dans l'éditeur.
4. Puis la correction.
```

**« Comment je la vérifie » est la question qui fait gagner du temps.** Une explication sans vérification vous fait essayer trois corrections au hasard.

## 🔴 L'IA se trompe à l'écran

![Deux langages, deux moments](/lecons/m07/07-m-ou-dax.svg)

On lui demande une colonne qui donne le chiffre d'affaires de Kinshasa. Elle répond :

```
= CALCULATE(SUM(Ventes[Montant_Local]) ; Ventes[Agence] = "Kinshasa")
```

C'est du **DAX**. Ça ne peut pas fonctionner dans l'éditeur Power Query — pas parce que c'est mal écrit, mais parce que **ce n'est pas le bon langage, ni le bon moment.**

| | Le langage M | Le langage DAX |
|---|---|---|
| **Quand** | **avant** le chargement | **après** le chargement |
| **Quoi** | il transforme la donnée | il calcule sur la donnée |
| **Où** | l'éditeur Power Query | le modèle de données |
| **Exécution** | à l'actualisation | à chaque clic de l'utilisateur |
| **Casse** | sensible | insensible |
| **Ça ressemble à** | `Table.SelectColumns`, `each`, `let … in` | `CALCULATE`, `SUMX`, `RELATED` |

**Pourquoi elle confond :** les deux vivent dans le même écosystème, les deux apparaissent dans les mêmes tutoriels, et la question « comment je calcule le CA de Kinshasa » ne dit pas *où* vous voulez le calculer.

### Quel V l'attrape

**`V1 — Version.** La question à se poser tient en une phrase :

> *« Dans quel éditeur est-ce que je vais coller ça ? »*

Si c'est l'éditeur Power Query, c'est du M. Si c'est une mesure du modèle de données, c'est du DAX. Le code est refusé **avant même de s'exécuter**, ce qui est la meilleure des erreurs : elle est immédiate et sans conséquence.

**La parade en une ligne, à mettre dans tous vos prompts :**

> *« Je veux du langage M, pour l'éditeur avancé de Power Query. Pas de DAX. »*

## Les autres erreurs typiques de l'IA sur le M

- **Elle invente des fonctions.** `Table.RemoveEmptyRows` n'existe pas. La vraie est `Table.SelectRows` avec une condition.
- **Elle se trompe de casse.** `Text.startsWith` au lieu de `Text.StartsWith`.
- **Elle mélange les versions d'Excel.** Certaines fonctions sont récentes ; le menu qu'elle décrit n'existe pas dans votre ruban.
- **Elle écrit des noms de colonnes en dur** sans qu'on lui demande. Toujours ajouter la contrainte.
- **Elle oublie le typage final.** Le code marche, et la colonne arrive en `any`.
- **Elle propose `Table.Buffer` comme remède à tout.** Ça casse le repliage de requête et ralentit sur les grosses sources.

## Chrono

| | Temps |
|---|---|
| **Classique** — chercher la bonne fonction dans la documentation, essayer | **2 h** *(ou on renonce)* |
| **Avec l'IA** — coller l'étape, demander de généraliser, tester | **12 min** |
| **Vérification obligatoire** — V1, un cas limite, un fichier cassé | **10 min** |

> **« Ou on renonce » n'est pas une figure de style.** Sans aide, la plupart des gens s'arrêtent à ce que l'interface sait faire — et c'est précisément la frontière entre une requête de démonstration et une requête qui tient.

## Les pépites 💎

**1. Toujours partir du code que l'interface a écrit.** Il utilise les bonnes fonctions et les bons noms. Généraliser un code juste est dix fois plus fiable que d'en faire écrire un à partir d'une description.

**2. « Dans quel éditeur est-ce que je colle ça ? »** La question qui attrape la confusion M / DAX en une seconde.

**3. Demander la vérification avant la correction.** « Comment je vérifie ta cause en trois secondes » vous évite d'essayer trois corrections au hasard.

## 🎯 Ton fichier à toi

Prenez une étape de votre propre requête qui vous gêne — celle qui dépend d'un nombre de lignes, d'un ordre de colonnes, ou d'un nom écrit en dur.

```
Je travaille dans Power Query, langage M, éditeur
avancé. Pas de DAX.

Voici l'étape que l'interface a générée :
[colle le code de la barre de formule]

Ce qui me gêne : [dis-le en français]

1. Réécris-la pour qu'elle ne dépende plus de ça.
2. Explique chaque fonction utilisée, en une ligne.
3. Dis-moi ce qui se passe si la colonne est absente,
   si la table est vide, si une valeur est nulle.
4. Donne-moi le bloc final, prêt à coller, avec des
   commentaires en français.
5. Dis-moi comment vérifier en trois secondes, dans
   l'éditeur, que ta version fait bien la même chose
   que la mienne sur mes données actuelles.
```

Le point 5 est celui qu'on oublie : **une réécriture plus robuste doit d'abord donner exactement le même résultat qu'avant.** Si elle ne le donne pas, c'est elle qui a tort — ou c'est votre ancienne étape qui était déjà fausse, et vous venez de l'apprendre.

> **Apportez au direct votre avant / après.** Le code M est le seul endroit du programme où la différence entre fragile et robuste tient en trois mots visibles à l'écran.

## Le problème

Le VBA est le seul endroit du programme où une erreur ne se voit pas à l'écran.

Une formule fausse affiche `#VALEUR!`, ou un nombre visiblement aberrant. Une macro fausse, elle, **tourne**. Elle finit. Elle affiche « Terminé ». Et elle a supprimé une ligne sur deux, ou écrit dans le mauvais classeur, ou laissé le calcul en manuel.

> **C'est aussi l'endroit où l'IA fait gagner le plus de temps — et celui où il faut le plus la vérifier. Les deux vont ensemble ; ce n'est pas une coïncidence.**

**Chrono** — méthode classique **1 journée** · avec l'IA **20 min** · **vérification 1 h**.

## La règle qui gouverne toute la leçon

> **On ne déploie jamais ce qu'on ne comprend pas.**

Ce n'est pas une précaution de débutant. Une macro tourne **sans surveillance**, sur les fichiers de quelqu'un d'autre, à une heure où vous n'êtes pas là. Le TP de ce module la note explicitement : un code non commenté vaut **zéro** au critère « usage critique de l'IA », quelle que soit sa qualité.

## ① Le bloc de contexte — la moitié du travail

```
J'écris une macro VBA pour Excel. Contraintes fermes :

- elle doit tourner sur Excel Windows ET Excel pour Mac
- donc : PAS de Scripting.FileSystemObject (n'existe pas sur Mac)
- donc : PAS de Application.FileDialog (n'existe pas sur Mac)
- les chemins utilisent Application.PathSeparator, jamais "\"
- Option Explicit en tête, toutes les variables déclarées
- Long, jamais Integer
- aucun chemin absolu : tout est relatif à ThisWorkbook.Path
```

**Les deux lignes sur macOS valent la moitié du prompt.** Sans elles, l'IA écrit du `FileSystemObject` neuf fois sur dix — non par erreur, mais parce que **c'est ce qu'elle a le plus vu** : le corpus VBA public est massivement écrit sous Windows.

C'est la même mécanique que le module 8 avec Power BI et Power Pivot, et que le module 9 avec le taux de change. **L'IA restitue son corpus. Votre terrain n'y est pas.**

## ② Décrire l'automatisation, pas le code

```
Décris-moi, en français et SANS CODE, les étapes qu'une macro
devrait suivre pour produire un PDF par ligne d'un tableau
de 12 lignes.

Pour chaque étape, dis ce qui peut mal se passer.
```

Vous obtenez six ou sept étapes **que vous pouvez valider avant qu'une ligne de code existe**. Et la colonne « ce qui peut mal se passer » est celle qui vous fera écrire la gestion d'erreur — au lieu de l'ajouter après le premier plantage, ce qui est toujours plus cher.

## ③ Exiger le code commenté ligne par ligne

```
Maintenant écris cette macro.

Exigence : CHAQUE ligne porte un commentaire en français qui dit
ce qu'elle fait ET pourquoi elle est là. Un commentaire qui
paraphrase le code ("incrémente i") ne compte pas.

Là où tu fais un choix — un type de variable, un ordre de
boucle, une valeur par défaut — dis pourquoi tu as choisi ça
plutôt qu'autre chose.
```

> 💎 **« Dis pourquoi tu as choisi ça plutôt qu'autre chose »** change la nature de la réponse. C'est là qu'apparaissent les décisions discutables — et donc celles que **vous** devez trancher.

Et les commentaires ne sont pas pour l'IA : ils sont pour vous dans six mois, et pour la personne qui reprendra le fichier quand vous serez ailleurs.

## ④ 🔴 L'IA se trompe à l'écran

![La même boucle, dans les deux sens](/lecons/m10/03-boucle.svg)

Demandez-lui une macro qui supprime les lignes vides d'une plage. **Neuf fois sur dix**, vous obtiendrez ceci :

```vba
For i = 1 To derniere
    If Cells(i, 1).Value = "" Then Rows(i).Delete
Next i
```

C'est propre. C'est lisible. **C'est faux.**

### Ce qui se passe réellement

Prenons cinq lignes : `Kinshasa`, vide, vide, `Dakar`, vide.

| `i` | La ligne `i` | Ce qui se passe | La plage devient |
|:--:|---|---|---|
| 1 | Kinshasa | on garde | K · v₂ · v₃ · D · v₅ |
| 2 | v₂ | **supprimée** | K · v₃ · D · v₅ |
| 3 | **D** | on garde | — |
| 4 | v₅ | **supprimée** | K · v₃ · D |

**La ligne v₃ a survécu.** Quand v₂ a été supprimée, v₃ est remontée en position 2 — et la boucle était déjà passée à 3.

Sur cinq lignes, une sur trois survit. Sur 5 637 lignes, ce sont des centaines de lignes vides qui restent, **et rien ne s'affiche**. La macro dit « Terminé ».

### La correction tient en trois caractères

```vba
For i = derniere To 1 Step -1
    If Cells(i, 1).Value = "" Then Rows(i).Delete
Next i
```

En remontant, supprimer la ligne 60 **ne déplace rien de ce qui est au-dessus**. C'est tout.

### Quel `V` l'attrape

| | Ce qu'il vérifie | Ici |
|---|---|---|
| `V1` | la source | ✓ |
| **`V2`** | **le calcul** | **✗ — les indices se décalent** |
| **`V3`** | **la cohérence** | **✗ — le compte final ne tombe pas** |
| `V4` | la vérité métier | — |
| `V5` | la lisibilité | ✓ **et c'est le piège : le code est beau** |

> **`V5` qui passe pendant que `V2` échoue, c'est la signature d'une erreur d'IA.** Un code mal écrit inspire la méfiance. Un code propre et faux ne l'inspire pas — c'est ce qui le rend dangereux.

### Le prompt qui l'attrape avant vous

```
Cette macro supprime des lignes dans une boucle.
Simule-la, pas à pas, sur cette plage :

  1  Kinshasa
  2  (vide)
  3  (vide)
  4  Dakar
  5  (vide)

Dis-moi, ligne par ligne, ce que vaut i, quelle ligne est
supprimée, et à quoi ressemble la plage après.
Puis compte les lignes vides restantes.
```

**Elle trouve son propre bug. Presque toujours.**

Et ce prompt est à garder, parce qu'il se généralise : *« simule ton code pas à pas sur ces données-là »* marche pour n'importe quelle boucle qui **modifie ce qu'elle parcourt** — supprimer des lignes, insérer des colonnes, déplacer des feuilles.

## ⑤ Faire expliquer une macro héritée

Le cas le plus fréquent en entreprise : un `.xlsm` que personne n'ose toucher, écrit par quelqu'un qui est parti.

```
Voici une macro trouvée dans un classeur hérité.
Personne ne sait plus ce qu'elle fait.

[le code]

Trois questions :
1. Qu'est-ce qu'elle fait, en trois phrases, en français ?
2. Qu'est-ce qu'elle MODIFIE ? Liste tout : cellules, feuilles,
   fichiers, réglages d'Application.
3. Qu'est-ce qui peut mal tourner si je la lance maintenant ?

Ne la réécris pas. Explique-la.
```

**La question 2 est celle qui compte.** Une macro qui laisse `Application.Calculation` en manuel, ou qui écrit dans un classeur ouvert à côté, fait des dégâts qu'on découvre trois jours plus tard — et qu'on n'attribue jamais à la bonne cause.

Et **« ne la réécris pas »** est nécessaire : sans cette ligne, vous obtenez une version « améliorée » que vous ne comprenez pas davantage, et qui ne fait plus tout à fait la même chose.

## ⑥ Les trois règles de sécurité

| La règle | Ce qu'elle évite |
|---|---|
| **Jamais de suppression sans confirmation** | `Rows.Delete` dans une boucle mal bornée efface une feuille en une seconde — et **`Ctrl+Z` ne remonte pas une macro** |
| **Toujours une copie avant le premier essai** | la première exécution est la seule qui compte : c'est là que le fichier est encore intact |
| **Toujours tester sur une copie du VRAI fichier** | trois lignes de test ne reproduisent aucun des cas qui cassent |

La deuxième mérite qu'on s'y arrête : **l'annulation ne fonctionne pas après une macro.** Excel vide la pile d'annulation dès qu'une macro touche le classeur. Ce que la macro a fait est fait.

## Ce que la leçon enseigne vraiment

L'IA écrit en vingt minutes une macro qui en prend une journée. Elle explique en trente secondes un code hérité que personne ne comprenait. Elle trouve son propre bug quand on lui demande de se simuler.

Et elle écrit, presque à chaque fois, une boucle de suppression dans le mauvais sens — **un code propre, lisible, et faux**.

> **Les deux faits sont liés. Ce qui la rend rapide, c'est qu'elle restitue ce qu'elle a vu. Ce qui la rend fausse, c'est exactement la même chose.**

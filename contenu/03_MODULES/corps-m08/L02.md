## Le problème

Le modèle est construit. Les six tables sont là, les cinq relations aussi.

Vous glissez `Montant_Local` dans un tableau croisé, et Excel affiche une somme. Ça marche. Mais c'est la somme de trois devises différentes : des francs congolais additionnés à des francs CFA. **Un nombre à huit chiffres qui ne veut rien dire.**

Il faut écrire ce qu'on veut vraiment calculer. Et pour ça, un langage : le **DAX**.

## Ce qu'on construit

Les huit mesures du modèle, et surtout la distinction qui bloque tout le monde pendant des mois.

## Mesure ou colonne calculée

![La distinction la plus mal comprise de la BI](/lecons/m08/03-mesure-ou-colonne.svg)

Les deux s'écrivent en DAX. Les deux ressemblent à des formules. **Et elles n'ont rien à voir.**

| | **Colonne calculée** | **Mesure** |
|---|---|---|
| Quand elle se calcule | à **l'actualisation** | à **l'affichage** |
| Ce qu'elle produit | une valeur **par ligne**, stockée | rien de stocké |
| Ce qu'elle coûte | de la mémoire, sur chaque ligne | rien |
| Où on peut la mettre | lignes, colonnes, filtres, segments | **valeurs uniquement** |
| Quand on en veut une | quand il faut **grouper par elle** | quand il faut **agréger** |

> **La question qui tranche, et elle suffit :**
> **« Est-ce que j'ai besoin de mettre ça EN LIGNE dans un tableau croisé ? »**
> Oui → colonne calculée. Non → mesure. **Et dans le doute, c'est une mesure.**

Une tranche d'âge, un segment, une clé composite : ce sont des colonnes calculées, parce qu'on veut voir les lignes du tableau croisé se découper selon elles.

Un chiffre d'affaires, un taux de marge, un nombre de clients : ce sont des mesures. Elles n'existent que dans la case où on les affiche.

**Et une mesure sur 1,2 million de lignes ne coûte rien**, parce qu'elle ne calcule jamais 1,2 million de valeurs : elle calcule **une** valeur, celle de la case affichée.

## Le contexte de filtre

![Une mesure ne connaît pas sa valeur : elle connaît son contexte](/lecons/m08/04-contexte-filtre.svg)

C'est le concept central du DAX, et il s'explique en une phrase avec un tableau croisé sous les yeux :

> **Une mesure ne connaît pas sa valeur. Elle connaît son contexte, et elle calcule dedans.**

Vous écrivez `CA USD` **une fois**. Dans un tableau croisé de six agences × deux années, elle est évaluée **douze fois** — et chaque fois dans un contexte différent :

- la case Kinshasa / 2026 voit `Agence = Kinshasa` **et** `Année = 2026` ;
- la case Total / 2026 ne voit que `Année = 2026` ;
- la case tout en bas à droite ne voit rien du tout, et rend le total général.

**Le contexte vient de trois endroits :** les étiquettes de lignes, les étiquettes de colonnes, et les filtres — dont les segments.

C'est tout. Et quand une mesure rend un chiffre qui vous surprend, la question à poser est toujours la même : **« qu'est-ce qu'elle voit, exactement, dans cette case ? »**

## Les fonctions, par ordre d'utilité

### Les agrégations

```
CA Local := SUM ( f_Ventes[Montant_Local] )
Quantité := SUM ( f_Ventes[Quantite] )
Clients actifs := DISTINCTCOUNT ( f_Ventes[Client_Cle] )
Nb Tickets := DISTINCTCOUNT ( f_Ventes[Ticket_Cle] )
```

**`DISTINCTCOUNT` est la fonction qui n'a pas d'équivalent raisonnable en formule.** « Combien de clients différents ont acheté ce mois-ci, dans cette agence, sur cette famille ? » — en formules, c'est une matricielle qui met trente secondes. Ici, c'est instantané, sur n'importe quelle combinaison.

### `DIVIDE` plutôt que `/`

```
Marge % := DIVIDE ( [Marge USD] ; [CA USD] ; 0 )
```

`DIVIDE` prend un troisième argument : **ce qu'on rend si le dénominateur est zéro**. Sans lui, une division par zéro produit une erreur qui remonte dans tout le tableau croisé.

`a / b` suivi d'un `IFERROR` fait la même chose, en plus lent et en plus long. **`DIVIDE` est la seule bonne réponse.**

### Les itérateurs — `SUMX`

`SUM` additionne une colonne. `SUMX` **parcourt une table ligne à ligne** en évaluant une expression sur chacune, puis additionne.

C'est ce qu'il faut dès que le calcul dépend de plusieurs colonnes :

```
Marge USD :=
SUMX (
    f_Ventes ;
    DIVIDE (
        f_Ventes[Montant_Local] * RELATED ( d_Produit[Taux_Marge] ) ;
        SWITCH ( RELATED ( d_Agence[Devise] ) ;
                 "CDF" ; RELATED ( d_Taux[CDF] ) ;
                 "XOF" ; RELATED ( d_Taux[XOF] ) ;
                 "XAF" ; RELATED ( d_Taux[XAF] ) )
    )
)
```

**`RELATED` va chercher une valeur dans une dimension**, en suivant la relation. C'est le `RECHERCHEV` du modèle — sauf qu'il ne coûte rien et ne recalcule jamais.

> **`SUMX` sur 1,2 million de lignes est rapide** — le moteur est fait pour ça. Ce qui est lent, c'est `SUMX` avec un `FILTER` ou un `LOOKUPVALUE` à l'intérieur : là, on refait une recherche par ligne.

### `CALCULATE` — la fonction centrale

```
CALCULATE ( <une mesure> ; <ce qui change le contexte> )
```

C'est **la seule fonction du DAX qui modifie le contexte de filtre**. Tout le reste en découle.

```
CA Kinshasa   := CALCULATE ( [CA USD] ; d_Agence[Agence] = "Kinshasa" )
CA toutes agences := CALCULATE ( [CA USD] ; ALL ( d_Agence ) )
Part de l'agence  := DIVIDE ( [CA USD] ; CALCULATE ( [CA USD] ; ALL ( d_Agence ) ) )
```

La troisième est celle qu'on utilise tout le temps : **le pourcentage du total**, qui reste juste quel que soit le découpage du tableau.

| Fonction | Ce qu'elle fait au contexte |
|---|---|
| `ALL ( table )` | **retire tous** les filtres de cette table |
| `ALL ( table[colonne] )` | retire le filtre de cette colonne seulement |
| `ALLEXCEPT ( table ; colonne )` | retire tout **sauf** cette colonne |
| `FILTER ( table ; condition )` | **ajoute** un filtre, ligne à ligne |
| `KEEPFILTERS ( … )` | ajoute sans remplacer |

> 🔴 **`FILTER` est puissant et lent.** Il parcourt la table. Sur une dimension de six lignes, aucun problème. Sur `f_Ventes`, on l'évite. **Quand un filtre simple suffit — `d_Agence[Agence] = "Kinshasa"` — on n'écrit pas `FILTER`.**

## Les mesures implicites, et pourquoi on les refuse

Quand vous glissez une colonne numérique dans la zone Valeurs d'un TCD branché sur le modèle, Excel fabrique une **mesure implicite** : « Somme de Montant_Local ».

Trois raisons de ne jamais les utiliser :

1. **Elle n'a pas de nom.** « Somme de Montant_Local » n'est pas un nom métier.
2. **Elle n'est pas réutilisable.** On ne peut pas l'appeler depuis une autre mesure.
3. **Elle disparaît** si on retire le champ, et avec elle tout ce qui en dépendait.

**On écrit ses mesures explicitement, toujours.** `Power Pivot > Mesures > Nouvelle mesure`, ou dans la grille de calcul en bas de la fenêtre Power Pivot.

## 💎 Nommer en français métier

```
❌  Mesure1    Somme de Montant_Local    CA_calc_v2
✅  CA USD     Marge %                   Clients actifs
```

Ce n'est pas de la coquetterie. **Le nom de la mesure est ce que la direction lit dans l'en-tête du tableau croisé.** Une mesure qui s'appelle « Marge % » produit un rapport lisible sans légende ; une mesure qui s'appelle « mesure3 » produit un rapport qu'il faut expliquer.

Et **rangez-les en dossiers** : dans la fenêtre Power Pivot, chaque mesure a une propriété *Dossier d'affichage*. `Chiffre d'affaires`, `Marge`, `Clients`, `Comparaisons`. Sur huit mesures c'est du confort ; sur quarante, c'est indispensable.

## Les huit mesures du modèle

```
CA Local        := SUM ( f_Ventes[Montant_Local] )

CA USD          := SUMX ( f_Ventes ;
                      DIVIDE ( f_Ventes[Montant_Local] ;
                          SWITCH ( RELATED ( d_Agence[Devise] ) ;
                                   "CDF" ; RELATED ( d_Taux[CDF] ) ;
                                   "XOF" ; RELATED ( d_Taux[XOF] ) ;
                                   "XAF" ; RELATED ( d_Taux[XAF] ) ) ) )

Marge USD       := SUMX ( f_Ventes ;
                      DIVIDE ( f_Ventes[Montant_Local] *
                                   RELATED ( d_Produit[Taux_Marge] ) ;
                          SWITCH ( RELATED ( d_Agence[Devise] ) ;
                                   "CDF" ; RELATED ( d_Taux[CDF] ) ;
                                   "XOF" ; RELATED ( d_Taux[XOF] ) ;
                                   "XAF" ; RELATED ( d_Taux[XAF] ) ) ) )

Marge %         := DIVIDE ( [Marge USD] ; [CA USD] ; 0 )
Clients actifs  := DISTINCTCOUNT ( f_Ventes[Client_Cle] )
Nb Tickets      := DISTINCTCOUNT ( f_Ventes[Ticket_Cle] )
```

*(Les deux dernières — `CA USD N-1` et `CA USD Cumul Annuel` — sont dans la leçon suivante.)*

**Remarquez `Marge %` :** elle n'additionne rien. Elle appelle **deux autres mesures**. C'est la bonne façon de faire — chaque mesure reste courte, et une correction dans `CA USD` se propage partout.

## Les pépites 💎

**1. Une mesure ne prend aucune place et se calcule à l'affichage.** Une colonne calculée occupe de la mémoire sur chaque ligne. Sur 1,2 million de lignes, la différence est le fichier entier.

**2. `DIVIDE(a ; b ; 0)`** gère la division par zéro sans `SIERREUR`, et c'est plus rapide.

**3. Nommer ses mesures en français métier.** « Marge % », pas « mesure1 ». C'est ce que la direction lit.

## Les erreurs fréquentes

- **Faire une colonne calculée là où une mesure suffit.** Le fichier gonfle et le calcul est figé.
- **Utiliser les mesures implicites.** Pas de nom, pas de réutilisation, et elles disparaissent.
- **`a / b` au lieu de `DIVIDE`.** Une erreur remonte dans tout le tableau.
- **`FILTER` sur la table de faits** quand un filtre simple suffit.
- **Écrire une mesure de cent lignes.** On en écrit trois de dix lignes qui s'appellent entre elles.
- **Oublier que le contexte vient aussi des segments.** Une mesure « juste » peut devenir fausse quand quelqu'un clique sur un segment que vous n'aviez pas prévu.

## Le mini-défi — 20 minutes

Sur le modèle de la leçon précédente :

1. Écrivez `CA Local`. Mettez-la dans un TCD par agence. **Regardez le total et dites à voix haute ce qu'il représente.** *(Rien.)*
2. Écrivez `CA USD`. Comparez.
3. Écrivez `Marge USD`, puis `Marge %` qui appelle les deux autres.
4. Écrivez `Clients actifs` et `Nb Tickets`.
5. Rangez les cinq en dossiers d'affichage.
6. Croisez `Clients actifs` par agence **et** par année : la somme des six agences ne fait pas le total. **Expliquez pourquoi.**

Le point 6 est le vrai exercice : un client qui achète dans deux agences est compté une fois par agence, et une seule fois au total. **`DISTINCTCOUNT` n'est pas additif** — et c'est exactement pour ça qu'on ne peut pas le pré-calculer dans une colonne.

**À retrouver, sur l'année 2026 :** CA USD **30 317 122,55** · Marge % **17,19 %** · Clients actifs **3 384** · Nb Tickets **318 799**.

## 🎯 Ton fichier à toi

Prenez les cinq indicateurs que votre service publie, et écrivez-les en DAX — même sans modèle sous la main. L'exercice est de **les formuler**, pas de les exécuter.

```
Voici le schéma de mon modèle :
[les tables, leurs colonnes, leurs relations. PAS les
données.]

Voici les cinq indicateurs que je publie aujourd'hui,
décrits en français :
[un par ligne, avec sa définition métier exacte]

1. Pour chacun : mesure ou colonne calculée ? Justifie
   en une ligne.
2. Écris la mesure en DAX, pour Power Pivot dans
   Excel 2024 — pas pour Power BI.
3. Explique-moi chaque mesure ligne par ligne, en
   français.
4. Pour chacune, dis-moi ce qu'elle rend dans le
   total général, et si ce total a un sens.
5. Signale-moi celles qui ne sont PAS additives, et
   ce que ça implique quand on les met dans un
   tableau croisé.
```

Le point 4 est celui qui attrape le plus d'erreurs : **beaucoup d'indicateurs justes au détail deviennent faux au total** — les moyennes, les taux, les comptages distincts.

> **Apportez au direct vos cinq définitions.** Écrire un indicateur en une phrase sans ambiguïté est plus difficile que d'écrire le DAX, et c'est là que les désaccords se révèlent.

## Chez vous, demain

Prenez l'indicateur de votre service dont personne ne sait exactement ce qu'il contient. Écrivez sa définition en une phrase, et faites-la valider par deux personnes.

Dans la moitié des cas, elles ne diront pas la même chose.
